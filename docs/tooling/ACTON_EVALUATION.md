## 1. Goal & Non-Goals

### 1.1 Goal (Issue #143 §1)

Evaluate whether [Acton](https://ton-blockchain.github.io/acton/) — an
all-in-one TON smart-contract toolchain built around the Tolk language —
should be adopted alongside or in place of the current **Tact + FunC +
TypeScript** stack, and produce an *explicit* adoption or non-adoption
decision **before** broad contract hardening work (D1, D2, A3, B1, B2)
depends on it.

### 1.2 Out of Scope (Issue #143 §4)

This evaluation does **not**:

- Migrate any Tact contract to Tolk.
- Rewrite production contract semantics to fit a toolchain.
- Change protocol economics, trust boundaries, or admin controls.
- Replace existing CI contract checks.
- Authorize mainnet deployment through Acton before A1, B1, B2 are READY.

### 1.3 Decision Summary (TL;DR)

| Question | Verdict |
|---|---|
| Adopt Acton as the *primary* toolchain? | **No** |
| Adopt Acton for *new* contracts? | **No** — no greenfield Tolk contract is on the roadmap |
| Phased migration of FunC helpers? | **No** — FunC files are frozen for A1/A2 audit |
| Permit Acton in an *isolated experiments sandbox*? | **Yes** — under `experiments/acton/` only |
| Broader migration proposal? | **Deferred** — gated on the four reconsideration triggers in §10 |

The detailed reasoning is in §6 (Compatibility findings) and §7
(Adoption decision).

## 4. Compatibility Prototype (Issue #143 §3 — Compatibility Prototype)

### 4.1 Posture

Per Issue #143 §3 the prototype must be **isolated** and **not change
the existing build path**. The compatibility prototype therefore lives
entirely under [`experiments/acton/`](../../experiments/acton/) and is
**explicitly not** wired into any CI job, `package.json` script,
`docker-compose*.yml`, or `scripts/setup.sh` flow.

The prototype documents:

1. Pinned install commands (Acton `v1.0.0`).
2. A reproducible `acton init` invocation against a clean `experiments/acton/playground/` directory (operator-driven, not CI-driven).
3. A minimal Tolk *harness* (`experiments/acton/tolk-harness/account-locks-toy.tolk` — illustrative source) that models the *shape* of one existing FunC helper (`contracts/payments/account-locks.fc`) so that the developer-workflow comparison in §5 has a concrete anchor.
4. A "what we did not migrate" register that records each frozen contract and the audit-freeze rule (`docs/audit-scope.md` §G.5) that prevented migration.

### 4.2 Why the prototype is *not* executed by CI

| Constraint | Source | Consequence |
|---|---|---|
| Acton binary not in the CI image | `.github/workflows/ci.yml` installs only Node 20 LTS | Adding a binary install step would be the very "CI addition" that Issue #143 §6 bars unless a migration is approved |
| Pinned Docker digest not yet published as a CI mirror | Acton README (project-side image only) | Supply-chain risk per Issue #143 §7 |
| Tact and FunC contracts are 🔒 frozen | `docs/audit-scope.md` §G.5 ("Prohibited During Freeze") | Any migration during freeze is itself the prohibited action |
| No greenfield Tolk contract exists | This evaluation §2.1 | An Acton CI job would have nothing to compile or test |

### 4.3 What the prototype demonstrates

The prototype is intentionally minimal. It demonstrates:

- The exact local install / init / test loop a future contributor would run.
- That Acton can scaffold an isolated workspace **without** touching `package.json`, `docker-compose*.yml`, `contracts/`, `scripts/deploy/`, or `.github/workflows/ci.yml`.
- That the on-chain semantics modelled (a `FRAUD_LOCK` / `COLLATERAL_LOCK` style bit-flag set) can be re-expressed in Tolk *syntax* — i.e. there is no language-level blocker for a future greenfield Tolk contract, only an organisational one (the freeze + the absence of a Tolk-first contract on the roadmap).

The full prototype README and the toy Tolk harness live at:

- [`experiments/acton/README.md`](../../experiments/acton/README.md)
- [`experiments/acton/tolk-harness/account-locks-toy.tolk`](../../experiments/acton/tolk-harness/account-locks-toy.tolk)

## 5. Workflow Comparison

Side-by-side of the same task ("write a contract test, profile its gas,
deploy to testnet, verify on-chain source") executed today vs. through
Acton.

| Step | Current (Tact + Jest + `@ton/sandbox`) | Hypothetical (Acton + Tolk) | Net change |
|---|---|---|---|
| **1. Scaffold** | `cd contracts/payment-hub && npm init` (already done) | `acton init` (creates `Acton.toml`, `contracts/`, `tests/`, `scripts/`) | Acton scaffolding only applies to a *new* Tolk project — no upgrade path for existing Tact projects |
| **2. Write contract** | `.tact` with strong-typed messages, structs, traits | `.tolk` with FunC-derived syntax | Two languages cannot be mixed in a single Acton project; mixing requires a second build system |
| **3. Write a test** | `tests/*.spec.ts` using `Blockchain.create()` + `await contract.send(...)` + `expect(transaction).toHaveTransaction(...)` | `tests/*.tolk` with `@test.contract` attribute + built-in matchers | Same expressiveness; Acton wins on co-located language but loses on JS ecosystem (`@jest/globals`, `ts-node`, `lodash`, etc.) |
| **4. Run the test** | `npm test` (Jest) | `acton test` | Equivalent runtime; Acton adds mutation and fork modes |
| **5. Gas snapshot** | Bespoke `scripts/gas-profile/*.ts` driven by `@ton/sandbox` traces (D2 will formalise budgets) | `acton snapshot` produces `.snap` files committed alongside source | Acton's snapshot ergonomics are stronger, *but* only for Tolk sources |
| **6. Deploy** | `scripts/deploy/deploy.ts` → uses `WalletContractV4` from `@ton/ton` | `acton deploy` reads wallet from `Acton.toml`, supports faucet top-ups | Acton wins on CLI ergonomics; existing deploy is the B2 runbook anchor and cannot be replaced before A1+B1+B2 are READY |
| **7. Source verification** | `scripts/deploy/check-immutability.ts` (code-cell hash) | `acton verify` (re-builds Tolk and matches on-chain cell) | Acton is *source-level*; current is *code-cell-level*. The current check is sufficient for our immutability guarantee (no upgrade paths). Source-level verification would require a Tolk re-implementation. |
| **8. CI** | `test-contracts` job in `ci.yml` (Node 20 only) | Additional `acton-test` job installing the v1.0.0 binary | Adds one CI dependency + supply-chain surface; gated by Issue #143 §6 ("preserve the current build path unless an explicit migration decision is approved"). |

**Conclusion:** Acton's developer experience is competitive *for new
Tolk projects* but offers **no incremental win for the existing Tact +
FunC + TypeScript stack** until a Tolk codebase exists.

## 6. Compatibility Findings

### 6.1 Tact — Not compatible

- Acton does not compile, lint, format, or test `.tact` files. The documentation indexes Tolk and (via `func2tolk`) FunC; Tact is absent from the supported-languages list and the v1.0.0 release notes.
- Adopting Acton for Tact contracts would mean **rewriting** every Tact contract in Tolk — explicitly out of scope per Issue #143 §4 and incompatible with the §G.5 audit freeze of `MerchantPaymentHub.tact`, `PaymentHub.tact`, `account-state.tact`, etc.
- **Verdict:** ❌ Blocker. No path forward without a separate architecture issue authorising the rewrite.

### 6.2 FunC — One-way translator only

- `acton func2tolk` produces *Tolk* output from FunC input. The output requires hand-review and equivalence testing.
- All four production FunC files (`account-locks.fc`, `nft_account_resolver.fc`, `payment-hub.fc`, `public-collateral-lookup.fc`, `diamond_resolver.fc`) are 🔒 frozen per `docs/audit-scope.md` §G.5 until A1/A2 verdict=READY.
- A "phased migration of selected FunC helpers" — one of the allowable decisions in Issue #143 §3 — therefore cannot start before A1/A2 close, and even then would require a separate issue *and* re-audit of the translated Tolk.
- **Verdict:** ❌ Deferred. Allowable path exists, but is gated on A1 + A2 + a dedicated issue.

### 6.3 TypeScript tests — Out of scope for Acton

- Acton's test runner consumes Tolk sources, not TypeScript. The existing `tests/*.spec.ts` suite would either remain in parallel or be rewritten as Tolk tests.
- The two are not interoperable: a Tact contract under test must be driven from `@ton/sandbox`, not from `acton test`.
- **Verdict:** ❌ Acton's test runner does not replace the existing TypeScript suite for Tact contracts.

### 6.4 Deployment scripts — Parallel, not replacement

- `scripts/deploy/deploy.ts` is the canonical B2 deploy entry point. Replacing it with `acton deploy` would invalidate the B2 runbook anchor and the immutability check chain.
- **Verdict:** ❌ Cannot replace before B2 is READY and a follow-up issue migrates the runbook.

### 6.5 CI contract job — Cannot change unilaterally

- Issue #143 §4 explicitly bars "Replacing existing CI contract checks before the evaluation is approved."
- Issue #143 §6 requires "preserve the current repository's Tact/FunC build path unless an explicit migration decision is approved."
- **Verdict:** ❌ No CI change permitted by this evaluation.

## 7. Adoption Decision (Issue #143 §3 — Adoption Decision)

Issue #143 §3 lists five allowable decisions. Each is evaluated against
the findings above.

| # | Decision | Verdict | Reasoning |
|---|---|---|---|
| 1 | **No adoption for the current roadmap** | ✅ **PRIMARY DECISION** | All in-scope blockers above prevent adoption; nothing on the F8 / D / A / B roadmap requires Tolk |
| 2 | **Optional tooling for experiments only** | ✅ **COMPANION POSTURE** | `experiments/acton/` permitted as a sandbox; explicitly excluded from `package.json`, CI, deploy chain |
| 3 | **Tolk/Acton for new contracts only** | ❌ Not recommended | No greenfield Tolk contract is on the roadmap. Introducing one without a dedicated design issue would split the toolchain and audit surface |
| 4 | **Phased migration of selected FunC helpers** | ❌ Blocked | Production FunC is frozen for A1/A2; reconsider after A2 verdict |
| 5 | **Broader migration proposal requiring a dedicated architecture issue** | ⏸ Deferred | Allowed if §10 reconsideration triggers fire, but does not need to happen now |

### 7.1 Why decision 1 + companion 2

The protocol's contract surface is **Tact-dominant** and **frozen for
audit**. Acton's incremental value (mutation, fork mode, snapshot
ergonomics) only materialises for Tolk source. Adopting Acton today
would either:

- **Split the toolchain** (Tact for production, Tolk for experiments) — doubling reviewer load with no offsetting safety win, *or*
- **Force a rewrite** in violation of Issue #143 §4 and the §G.5 freeze.

The companion "experiments only" posture lets the team continue to
*learn* Acton (so a future Tolk contract is not greenfield to the
team) without paying the toolchain-split cost.

### 7.2 Existing tooling that remains authoritative

Per Issue #143 §5.3 the following remain the canonical paths and **must
not** be replaced by an Acton equivalent without an approved follow-up
issue:

| Concern | Authoritative tool | Anchor |
|---|---|---|
| Tact compilation | `@tact-lang/compiler` via `contracts/payment-hub/npm run build` | `.github/workflows/ci.yml` `test-contracts` job |
| FunC compilation | TON Labs FunC compiler | `contracts/payments/account-locks.fc` build |
| Contract tests | Jest + `@ton/sandbox` + `@ton/test-utils` | `tests/*.spec.ts` |
| Invariant tests | Jest property-based | `tests/invariants/` |
| Adversarial + fuzz | Jest with coverage gate ≥ 80 % | `tests/adversarial/` |
| Gas profiling | `scripts/gas-profile/` (TypeScript) | D2 anchor |
| Deployment | `scripts/deploy/deploy.ts` | B2 runbook anchor |
| Verification | `scripts/deploy/check-immutability.ts` + `scripts/deploy/verify.ts` | B1 / B2 |
| F-series readiness validators | `scripts/{bridge,recurring-payments,multisig,dex,analytics}/check-*-readiness.ts` | F3..F7 |

## 8. Migration Cost & Risk Estimate (Issue #143 §5.1)

Even though the primary decision is **no adoption**, Issue #143 §5
requires documenting what a hypothetical migration would cost, so that
future reconsideration has a calibrated baseline.

### 8.1 Cost estimate — partial migration of FunC helpers (decision 4)

| Cost driver | Estimate | Notes |
|---|---|---|
| FunC → Tolk translation (5 files: `account-locks.fc`, `nft_account_resolver.fc`, `payment-hub.fc`, `public-collateral-lookup.fc`, `diamond_resolver.fc`) | 3–5 dev-days per file | `acton func2tolk` is one-way + lossy; output requires line-by-line review against the original |
| Equivalence test suite (Tolk vs FunC code-cell hash + behaviour) | 5–8 dev-days | New test category; must run side-by-side until decommission |
| Re-audit of translated Tolk | A2-class engagement | Cannot reuse A1 verdict because the source language changed |
| CI integration (install Acton binary, pin digest, gate on `acton test`) | 1–2 dev-days | Plus ongoing supply-chain triage of every Acton release |
| Runbook updates (B1/B2/`docs/audit-scope.md` §G.2) | 1–2 dev-days | Including `sha256sum` table refresh in §G.6 |
| Documentation updates (4 + F-series, D-series specs, INDEX) | 2–3 dev-days | High-risk for documentation drift |
| **Total** | **~20–35 dev-days + one A2-class audit** | Plus permanent maintenance overhead for the second toolchain |

### 8.2 Cost estimate — full Tact → Tolk migration (decision 5)

| Cost driver | Estimate |
|---|---|
| Tact → Tolk rewrite (20 `.tact` files, including 6 production contracts) | 4–8 weeks of focused engineering |
| Re-audit of every rewritten contract | A1 + A2 re-engagement |
| Off-chain test rewrite (`tests/*.spec.ts` → `tests/*.tolk`) | 2–3 weeks |
| Loss of Tact-specific safety features (typed messages, traits) | Qualitative regression |
| **Total** | **3–4 months of contract engineering + two audit re-engagements** |

This is the strongest argument against decision 5 today: the marginal
toolchain win does not justify a 3–4 month freeze on every other Track
A / B / D / F deliverable.

### 8.3 Risk register

| Risk | Severity | Mitigation |
|---|---|---|
| Audit-freeze violation if migration starts before A1/A2 verdict | **Critical** | Defer all migration work; gate on `docs/audit-scope.md` §G.7 |
| Loss of equivalence between FunC and translated Tolk | **High** | Equivalence test suite (§8.1 row 2); side-by-side run until decommission |
| Supply-chain attack on the Acton binary / Docker image | **High** | Pin to `v1.0.0` digest; gate CI on a vendored mirror; mirror to `docs/security/audits/` evidence trail |
| Toolchain split (Tact + Tolk in production) | **High** | Adopt decision 1 (no migration) or decision 5 (full migration); reject hybrid |
| Documentation drift between Tact source and Tolk re-implementation | **Medium** | Equivalence tests as the source of truth; CI gate per Issue #143 §6 |
| Lost reviewer fluency (Tact reviewers ≠ Tolk reviewers) | **Medium** | Companion "experiments only" posture lets the team build Tolk fluency *before* a migration |
| Mainnet deployment without B1/B2 sign-off using `acton deploy` | **Critical** | Issue #143 §4 explicitly bars this; runbook stays at `scripts/deploy/MAINNET_RUNBOOK.md` |

## 10. Reconsideration Triggers

This decision is reviewed when **any one** of the following fires:

1. **A1 + A2 both verdict=READY** — contracts unfreeze, FunC helpers become eligible for migration; revisit decision 4.
2. **A greenfield Tolk-first contract is proposed** — e.g. a new diamond facet or a new off-chain-anchored proof verifier; revisit decision 3 with a dedicated architecture issue.
3. **Acton adds first-class Tact support** — would unblock decisions 3 and 5 without a rewrite.
4. **A high-severity gap in the current toolchain** — e.g. an audit finding that Jest + `@ton/sandbox` missed a class of bugs that Acton mutation testing would catch; revisit decision 1.

Until any trigger fires, the decision in §1.3 and §7 stands.
